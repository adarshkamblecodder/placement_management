REFERENCE STRUCTURE  (mernt project — the target pattern)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The mernt reference project uses a flat src/ structure:
  src/
    app.js
    server.js
    config/         (database.js, env.js)
    models/         (one file per model)
    controllers/    (one file per domain)
    routes/         (one file per domain)
    services/       (one file per domain)
    middleware/     (error.middleware.js, validation.middleware.js)
    utils/          (generateToken.js)
    validators/     (auth.validator.js)

Our project uses a domain-module pattern (modules/admin/*, modules/student/*).
This is intentional because the project is larger. The key principle is the same:
  - config/       → configuration only
  - models/       → data layer only
  - routes/       → HTTP layer only (thin, delegates to controllers/services)
  - controllers/  → orchestration (calls services, builds response)
  - services/     → business logic (DB queries, file ops, emails)
  - validators/   → input validation only
  - middleware/   → Express middleware only
  - utils/        → pure helper functions (no side effects)

WHERE TO PUT NEW FILES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  New admin feature?
    → src/modules/admin/<featureName>/routes/<featureName>.routes.js
    → Register in src/modules/admin/index.js
    → Mount in src/routes/index.js

  New student-facing page?
    → src/modules/student/routes/<featureName>.routes.js
    → Register in src/modules/student/index.js
    → Mount in src/routes/index.js

  New DB model?
    → src/db/models/<modelName>.js
    → Add associations to src/db/models/index.js
    → Export from index.js module.exports

  New shared service (email, audit, etc.)?
    → src/shared/services/<name>.service.js

  New shared utility (pure function)?
    → src/shared/utils/<name>.js

  New middleware?
    → src/shared/middleware/<name>.js

  New template?
    → templates/tracker/<name>.html
    → Extend base.html: {% extends 'base.html' %}

  New seed/migration script?
    → scripts/<name>.js   (if one-time/utility)
    → seed_students.js    (if it seeds test data for dev)

  Config values?
    → src/config/env.js   (add to the exports)
    → .env.sample         (document the new key)
    → NEVER hardcode in route or service files

CORE DATA FLOW (how the main placement pipeline works end-to-end)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  1. COMPANY SETUP
     Admin → /companies/ → Create Company → Add PlacementDrive
     Drive has: jobRole, interviewDate, minCGPA, packageLPA, numberOfOpenings
     Admin adds InterviewRounds to the drive (Round 1, Round 2, ...)

  2. SHORTLISTING
     Admin → /students/ → checkbox select students → choose drive → Confirm
     POST /shortlists/save → creates Shortlist + ShortlistStudent records
     Email sent to each shortlisted student via notification.service

  3. INTERVIEW ROUNDS
     Admin → /shortlists/ → expand shortlist → click "Rounds" button for student
     GET /admin/interview-rounds/:driveId/student-results/:studentId
     Returns rounds with pre-filled dates from drive.interviewDate
     Admin updates result (Passed/Rejected) per round
     POST /admin/interview-rounds/save-result  (with X-CSRF-Token header)
     syncStudentStatus() called after each save:
       - Rejected in any round → placement_status = "Rejected in Interview"
       - Passed round N → placement_status = "N Round Qualified"
       - ALL rounds passed → placement_status = "Placed", sets placement_company,
         placement_package, placement_year from the drive record

  4. PLACED STUDENTS
     Students with placement_status = "Placed" appear in /placed/
     Admin can also manually update via /students/:pk/placement/
     acceptOffer() in offerConflict.service.js handles offer + one-offer enforcement

  5. STUDENT SELF-SERVICE
     Student logs in → /student/profile/ (view) or /student/my-profile/ (edit)
     Can add: internships, projects (LIVE or NORMAL), upload resume, update profile
     All changes logged to AuditLog (action = STUDENT_PROFILE_UPDATED, etc.)
     Visible to admin at /admin/notifications/
