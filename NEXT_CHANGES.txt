THE CORE PROBLEM — How a real drive actually works vs what the system does
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

REAL WORLD (how a TPO runs a campus drive):
  - A company says: "We have 5 openings."
  - I (TPO) look at eligible students and shortlist 20-30 of them to APPEAR
    for the interview. All 20-30 students sit in Round 1 (aptitude test).
  - After Round 1: maybe 15 qualify → they go to Round 2 (technical).
  - After Round 2: maybe 8 qualify → they go to Round 3 (HR).
  - After Round 3: company picks the best 5 → those 5 get the offer.
  - The "5 openings" is the FINAL SELECTION CAP, not the shortlist cap.

WHAT THE SYSTEM DOES TODAY:
  - It BLOCKS the TPO from shortlisting more than numberOfOpenings students.
  - So if there are 5 openings, only 5 students can be shortlisted.
  - This means only 5 students appear for Round 1.
  - If 2 of them fail Round 1, you're left with 3 students for the company.
  - The company gets 3 hires instead of 5 — just because the system was wrong.

  This is the biggest functional bug in the entire product.

CHANGE 1 — CRITICAL: Remove the openings cap from shortlisting
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PROBLEM:
  In shortlists.routes.js (POST /shortlists/save):
    if (studentIds.length > openings) → BLOCKS the shortlist creation

  In student_list.html:
    - The "Select All" button respects the openings limit
    - Checking more than `openings` students shows an error
    - The openings badge says "X / limit selected"
  
  All of this treats numberOfOpenings as a SHORTLIST cap. It should be
  treated as a FINAL OFFER cap.

WHAT TO CHANGE:

  1. shortlists.routes.js
     REMOVE this block entirely:
       const openings = Number(drive.numberOfOpenings);
       if (Number.isFinite(openings) && openings > 0 && studentIds.length > openings) {
         return res.status(400).json({ success: false, error: "..." });
       }
     Replace with a WARNING in the response (not a block):
       if (studentIds.length > openings) {
         // just log it — don't block
       }

  2. student_list.html
     - Remove the selection limit logic entirely from JS.
       The openings badge should show as INFO only: "X openings available"
       not as a hard cap that prevents selection.
     - "Select All" should select ALL visible students, not limited to openings.
     - The warning "This drive has only X openings, extra selections removed"
       should be REMOVED completely.
     - The Shortlist button should only be disabled when 0 students are selected,
       not when count > openings.

  3. The openings number should only be used at the END:
     When syncStudentStatus() marks a student as Placed, check:
       "How many students from this drive are already Placed?"
       If count >= numberOfOpenings → show a warning to TPO that the drive
       is now FULL (all openings filled). Don't block — just inform.

CHANGE 2 — HIGH: ShortlistStudent needs a per-student status field
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PROBLEM:
  The ShortlistStudent table only has: id, shortlistId, studentId, createdAt.
  There is no status on the shortlist entry itself.
  
  As a TPO, in the shortlist I need to see at a glance:
    - Which students are still in the running (Active)
    - Which were rejected at a round (Rejected)
    - Which received the final offer (Selected / Offered)
    - Which declined the offer (Offer Declined)
    - Which did not appear (Absent)

  Right now, the student's global placement_status is the only indicator,
  but that mixes up ALL their drives. If a student is in 3 shortlists
  (TCS, Infosys, Wipro) and gets rejected in TCS Round 1, their status
  becomes "Rejected in Interview" globally — which is wrong. They can still
  appear in Infosys and Wipro drives.

WHAT TO CHANGE:

  1. Add a `status` field to the ShortlistStudent model:
       status: ENUM(
         "Shortlisted",      — appeared/active in this drive
         "Absent",           — did not appear for the interview
         "Rejected",         — eliminated during rounds
         "Selected",         — passed all rounds, got the offer
         "Offer Declined",   — got offer but rejected it
         "Withdrawn"         — removed by TPO
       )
       Default: "Shortlisted"

  2. When syncStudentStatus() marks a student as "Rejected in Interview"
     for a round:
     → Update ShortlistStudent.status = "Rejected" for that specific
       shortlistId + studentId combination
     → Do NOT change global placement_status to "Rejected in Interview"
       (unless student is rejected in ALL active shortlists)

  3. When student passes all rounds:
     → Update ShortlistStudent.status = "Selected"
     → Update Student.placement_status = "Placed" (this part is correct)

  4. In the shortlist page table, show a status badge per student row
     so the TPO can see per-drive status at a glance.

  5. Add a button on shortlist page: "Mark as Absent" for students who
     did not show up for the interview.

CHANGE 3 — HIGH: Drive lifecycle / status is not being used properly
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PROBLEM:
  PlacementDrive has driveStatus: ENUM("upcoming", "ongoing", "completed")
  and lifecycleStage: STRING.
  But these are never automatically updated. A drive that happened 3 months
  ago still shows as "upcoming" because nothing changed it.

  As a TPO, I need to know which drives are active right now vs done.

WHAT TO CHANGE:

  1. Auto-update driveStatus based on interviewDate when the drive is loaded:
     - If interviewDate > today → "upcoming"
     - If interviewDate == today → "ongoing"
     - If interviewDate < today → "completed"
     (Can be done in the GET route or as a pre-read hook)

  2. On the companies page where drives are listed, show the driveStatus badge
     with color:
     - Upcoming → blue
     - Ongoing → green (pulsing dot)
     - Completed → grey

  3. Add a filter on /shortlists to show only "ongoing" or "upcoming" drives
     by default, with option to see completed ones.

  4. When a drive is "completed", the TPO should see a summary:
     - Total shortlisted: N
     - Appeared: N
     - Selected (got offer): N  ← ShortlistStudent.status = "Selected"
     - Rejected: N
     - Openings filled: X / Y

CHANGE 4 — HIGH: Student global placement_status is overloaded and wrong
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PROBLEM:
  A student's placement_status on the Student model is currently used to
  track per-drive interview progress:
    "Shortlisted", "First Round Qualified", "Rejected in Interview" etc.

  This is wrong. A student can be in multiple drives simultaneously:
    - Shortlisted at TCS → "Shortlisted" overwrites previous status
    - Rejects Round 1 at TCS → "Rejected in Interview"
    - But they are still active at Infosys → status is now misleading

  The global placement_status should only reflect the student's overall
  placement outcome, not per-drive progress.

WHAT TO CHANGE:

  Student.placement_status should only have these values:
    "Not Placed"    — default, no offer accepted yet
    "Placed"        — has accepted an offer (final state)

  Per-drive status (Shortlisted, Rejected, Round Qualified, etc.) should
  live ONLY on ShortlistStudent.status (see Change 2).

  The student list filter "Active Unplaced" = placement_status = "Not Placed"
  The placed list = placement_status = "Placed"
  Everything else goes on the shortlist view, not on the student card.

  syncStudentStatus() should be simplified:
    - Only set "Placed" when all rounds are qualified
    - Otherwise, update ShortlistStudent.status for that drive
    - Never set intermediate statuses on the global Student record

PROBLEM:
  A single PlacementDrive can have MULTIPLE Shortlists (the model allows it).
  If I create "TCS Drive" and shortlist 10 students, then create another
  shortlist for the same TCS Drive with 5 more students — there are now 2
  shortlists, both linked to the same drive and the same set of rounds.

  When I open the round results modal, it shows all rounds for the drive.
  But which shortlist's students are we tracking? Both? It's unclear.

  As a TPO, I typically have ONE shortlist per drive (the list of students
  who will appear for that company's interview).

WHAT TO CHANGE:

  Option A (simpler): Enforce one shortlist per drive.
    - When creating a shortlist, check if one already exists for that drive.
    - If yes, ask: "A shortlist already exists for this drive.
      Do you want to add these students to the existing shortlist, or
      create a new shortlist?"
    - This prevents accidental duplicates.

  Option B (current model, just show it better): 
    - In the shortlists page, group by Company/Drive, not by individual shortlist.
    - Show all students across all shortlists of the same drive together.
    - This is a UI change, not a data change.

  Recommendation: Go with Option A. Simpler for a TPO.
